# 计划文档

**计划文件是事实来源，不是对话。** 这个仓库两边都在用 AI 改
（我们用 Claude Code，tim.lu 用 Codex），会话随时中断、上下文随时丢——
写进 `Plan/` 的东西才留得下来。

计划**提交进仓库**，和代码一起走。现有的：

| 文件 | 内容 |
|---|---|
| `Plan/plan.md` | v2 总体规划 |
| `Plan/game3-improvements.md` | v3 诊断与改造（含实测数据） |
| `Plan/game3-visual.md` | v3 视觉化计划 |
| `Plan/v1v2-fun.md` | v1/v2 好玩度诊断 |

**照着现有文件的写法来**：中文、有诊断、有实测数字、有取舍理由。

## 1. 先把范围问清楚

不要带着模糊的理解开写。反复问到双方**没有认知缺口**为止——
没问出口的问题，就是以后的 bug。尤其要问清楚：

- 动的是哪个游戏？（v1/v3 是 tim.lu 的地盘，改之前想清楚怎么减少冲突面）
- 是数值/内容改动，还是机制改动？（前者必须重跑 `/v3-balance`）
- 有没有「不许动」的东西？（比如 tim.lu 手写的 `authoredEvents` 与 `CHALLENGES` 就是原样保留的）

## 2. 文档结构

```markdown
# <标题>

## 一、诊断：现在哪里不对
用**实测数据**说话，不要只写感觉。
「随机乱选 14 局，仁政之世一次都没出现」比「结局不平衡」有用得多。

## 二、要改什么
### 1. <改动名>
- [ ] 具体动作（动了哪个文件的什么）
- [ ] ...
**为什么**：一句话说清动机
**验收**：怎么算做完了（可执行的命令 / 可观察的数字）

## 三、实施方式（降低协作冲突）
新增内容尽量进**新文件**，在已有文件里只留最小接入点。
v3 就是这么干的：机制进 rules.ts / meta.ts / events.ts，App.tsx 只改几行。

## 四、验收方式
- `npx tsc --noEmit && npm run build` 全绿
- Playwright 无头实跑（见 /verify）
- 数值改动：`/v3-balance` 45 局，胜率对照基准

## 五、进度与交接
- [x] 已完成的项 —— 附实测结果
- [ ] 未完成的项 —— 卡在哪、下一步做什么
```

## 3. 边做边勾

改完一项就回来把 `[ ]` 改成 `[x]`，**并把实测数字写上**。
`Plan/game3-improvements.md` 里那句「当前基准：随机乱选 45 局 → 17 胜 23 败 5 崩殂（38% 胜率）」
就是这样留下来的——它后来成了所有数值改动的对照基准。

## 4. 计划变了要改文档

发现原方案行不通，改文档，并写清楚**为什么换路子**。
被推翻的方案也留一句话，免得下一个会话又走一遍死路。

## 什么时候不用这个

单次会话能做完的改动，直接做。改一个数值、修一个显示 bug，
写计划文档的成本比改动本身还高。
